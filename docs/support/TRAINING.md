# Local support-model training experiment

The regression tester itself does not need model training. This optional experiment
fine-tunes a small LoRA adapter for the local Qwen support agent so we can evaluate
whether training improves actual tool decisions. It trains an existing language
model; it does not train a foundation model or learn from real customers.

The base is `Qwen/Qwen3-4B-Instruct-2507`, using the Apache-2.0 licensed MLX 4-bit
conversion `mlx-community/Qwen3-4B-Instruct-2507-4bit`. Base weights remain unchanged.
The adapter and downloaded weights stay in the ignored `.models` directory.

## Data and separation

`agent_regression.support.training` generates synthetic policy-expert conversations
with separate order families, customer requests, and request keys. It does not
copy the canonical 22 regression scenarios or derive labels from the model's
recorded behavior. Training, validation and training-corpus test partitions use
separate identifiers and wording. They exercise the same public business policy;
they are not a benchmark for unseen customer domains.

Each JSONL record contains `messages` and the three current `tools` schemas. There
is one record per assistant decision, ending in either an actual tool call or a
final answer. A lookup and its completed response become context for the next
refund/escalation decision. This matters because MLX's `--mask-prompt` supervises
only the last assistant message: one full conversation per record would mostly
teach final replies while leaving intermediate actions untrained.

The first corpus has 384 training decisions from 168 requests, 48 validation
decisions from 21 requests, and 48 training-corpus test decisions from another
21 requests, covering 21 policy and intent categories. Training targets include
144 lookups, 32 refunds, 40 escalations and 168 final replies. These are synthetic
expert actions, not successful traces generated by the model being trained.

The script renders every record through the model's native Qwen chat template.
It checks that the masked prefix matches that template's generation prefix, native `<tool_call>` targets
preserve names and arguments, supervised targets are nonempty, and no record is
truncated. A token-length limit failure stops before model training.

Actual preflight for the first run found 1424–1713 training tokens per record,
1423–1703 validation tokens, and 21–62 supervised target tokens. The actual run
therefore uses `--max-seq-length 2048`, with zero truncated records.

The canonical regression suite stays separate and checks attempted calls,
arguments, order and counts. Adapter evaluation must run the same suite with the
same prompt/settings/repeat count as the baseline. Training loss alone cannot
establish better agent behavior. Improvements on this small suite also do not
establish general safety or usefulness to outside developers.

## Reproduce locally

Use Apple Silicon with enough available memory, the optional local MLX environment,
and the already downloaded base model. Stop local inference before training to
avoid keeping two copies of the model in memory. Normal package installation and
offline regression tests do not install MLX.

```sh
.venv-model/bin/python -m agent_regression.support.training --output .training-data/support-native
.venv-model/bin/python scripts/train_support_model.py \
  --data .training-data/support-native --adapter .models/support-lora-native \
  --manifest reports/support-training-native.json \
  --experiment synthetic-support-decision-lora-native-v2 \
  --iters 384 --max-seq-length 2048 --prepare-only
.venv-model/bin/python scripts/train_support_model.py \
  --data .training-data/support-native --adapter .models/support-lora-native \
  --manifest reports/support-training-native.json \
  --experiment synthetic-support-decision-lora-native-v2 \
  --iters 384 --max-seq-length 2048
```

The wrapper defaults remain 150 updates and a 4096-token maximum sequence length.
The displayed current native-v2 commands deliberately override those defaults
with 384 updates and a 2048-token limit. Both experiments use batch size 1, the
last eight model layers, rank 8 LoRA, learning rate 0.0001, prompt masking,
gradient checkpointing and a fixed seed. Validation runs at the start, every
50 updates and the end. These are bounded exploratory runs, not a claim that
the settings are optimal.

Each validation check samples 10 of the 48 validation records through NumPy's
permutation order. Successive checks may therefore use different subsets. The
fixed seed makes the run reproducible; it does not make those reported losses a
paired comparison of identical records. The first experiment selected its
final step-150 adapter; native-v2 selected its final step-384 adapter. Both run
lengths were predetermined, rather than picking a checkpoint with the lowest
loss from changing validation subsets. The independent fixed regression suite
supplies the before/after behavioral comparison.

The script explicitly seeds NumPy's batch sampler. MLX-LM's `train_model` seeds
MLX for adapter initialization separately. This is required because the script
calls `train_model` directly to retain local loss-report callbacks; the library's
usual `run` wrapper normally supplies the NumPy seed. An initial exploratory run
was interrupted after this missing seed was found during independent review.
Its manifest/log are preserved as `support-training-unseeded-interrupted.*` and
excluded from the adapter experiment results. The completed experiment must use
the corrected, seeded script.

The first corpus combines the policy and trusted application context into one
system message. Its first behavioral evaluation used a live Pydantic AI client
that sent those as two system messages, changing token ordering around tools.
The current factory sends one combined system message, tested against the
corpus's exact instruction content. The first corpus still differs from live
inference in strict-tool metadata, JSON object key ordering in tool schemas,
and tool-response serialization. These differences were discovered by rendering
captured HTTP requests with the actual native tokenizer. Preflight alone checks
the dataset template's masked prefix; exact training/inference parity also needs
that HTTP capture. None of these formatting findings establish what caused an
individual behavioral failure.

The script requires existing project-local model and dataset paths. It sets
offline Hugging Face/Transformers environment flags, does not trust remote code,
and uses no hosted API or remote experiment logger. Existing corpus files and
adapter weights are preserved: when repeating these commands, choose fresh
`--output`/`--data`, `--adapter` and `--manifest` paths. A prepare-only manifest
can be reused to start its prepared run; completed artifacts cannot be overwritten.

`reports/support-training.json` records dataset hashes and provenance, base-model
revision and file hashes, runtime versions, hyperparameters, loss reports, elapsed
time and adapter hashes. Training is marked completed only after weights are
saved. Failure or interruption is recorded and propagated. Keep the manifest with
the corresponding independent evaluation report when comparing experiments.

The initial real-model suite found missing refund/escalation calls and guessed
ambiguous identifiers. We then rewrote the general safe instructions into an
explicit decision procedure. Before generating training data, the lookup tool
description's concrete example identifier was removed to avoid exposing a
canonical evaluation ID in every training schema. The baseline therefore used a
slightly different tool description; comparisons must disclose this small schema
change rather than attribute every difference solely to the adapter.

## Completed local run

The corrected, seeded run completed all 150 updates and saved its final adapter.
The manifest records October 11, 2026, 7:05:06 pm to 8:00:14 pm in
America/Toronto. That wall-clock span is 55 minutes 7.9 seconds; the separately
measured model-loading/training/save block is 1423.386 seconds, or 23 minutes
43.4 seconds. These measurements have different scopes/time sources: the
training timer begins after preflight and base-file hashing. The report preserves
both measurements and makes no assumption about the remaining difference.

The final 10-update mean training loss was 0.095963. Final reported validation
loss was 0.084330 at 149 completed updates, immediately before the final update.
It used a 10-record subset of the 48 validation records, so these loss reports
are training diagnostics rather than a paired agent-quality benchmark. Peak MLX
allocated memory was 4.396 GB. The independent regression evaluation is separate.

The final `.models/support-lora/adapters.safetensors` contains 14,692,068 bytes.
Its SHA256 is `785a7bb1fb5395dd60635324b064993b3a456c0e5a791f1d21740e08a3d9e2ae`,
identical to `.models/support-lora/0000150_adapters.safetensors`. Checkpoints at
50 and 100 updates are also preserved in the same directory. Selection used the
predetermined final step, not validation-loss checkpoint selection. The source
conversion revision was `50d427756c6b1b2fe0c0a10f67fbda1fc8e82c1b`.

`reports/support-training.json` and `reports/support-training.log` contain the
completed run's metadata and logs. This confirms actual local adapter training;
it does not establish improved agent behavior. The first paired evaluation
passed 54 of 102 adapter runs versus 60 of 102 base runs. Those results are
preserved; the low training loss did not translate into a better support workflow.

## Separate native-format experiment

The second experiment completed with the same synthetic expert cases,
split identifiers, wording, policy and expected behavior. Its native-format
corpus corrects tool metadata, object key order, tool-response JSON and prior
assistant argument representation to match the actual live inference path.
All 480 saved prefixes across 210 synthetic requests were independently compared
with actual mocked OpenAI HTTP messages, installed MLX message normalization and
the native Qwen tokenizer. Every training, validation and training-corpus test
prefix matched token-for-token. This checks serialization, not model quality;
expert assistant decisions supplied the mocked responses. The proof is recorded
in `reports/support-native-prefix-parity.json`. The first corpus and adapter
remain preserved for comparison.

This run uses 384 predetermined updates, batch size 1, the same last-eight-layer,
rank-8 LoRA settings, learning rate 0.0001, seed and gradient checkpointing. That
is one pass through 384 decision records. It uses fresh paths:
`.training-data/support-native`, `.models/support-lora-native`, and
`reports/support-training-native.json`. The final adapter is selected by that
fixed run length, not by regression results or the changing validation subsets.
The manifest records the explicit experiment label, actual corpus version,
training-script hash and data hashes. This is a second bounded experiment;
its independent behavioral evaluation is separate from training completion.

Native preflight found 1435–1694 training tokens, 1434–1684 validation tokens and
21–62 supervised target tokens, with zero truncation at the 2048-token limit.

The seeded native-v2 run completed all 384 updates. Its manifest records
October 11, 2026, 8:32:33 pm to 10:20:03 pm in America/Toronto. The recorded
wall-clock span is 6450.605 seconds (1 hour 47 minutes 30.6 seconds); the separate
model-loading/training/save timer is 3772.703 seconds (1 hour 2 minutes
52.7 seconds). Both measurements are preserved, with their different scopes
and time sources; the report does not infer the cause of the remaining difference.

Final reported training loss was 0.101811, averaging only the last four updates
(381–384), because the run length is not a multiple of the 10-update reporting
interval. Final sampled validation loss was 0.075271 at 383 completed updates,
before update 384, using 10 of the 48 validation records. Peak MLX allocation
was 4.355 GB. These losses do not establish better tool decisions.

The selected final `.models/support-lora-native/adapters.safetensors` is
14,692,068 bytes, with SHA256
`6d8cc76a1e9d53c8156b0bdfa1db692f2b7534c33b32b22449ab6b69bf1f2e2f`.
Its 112 tensors are finite, and all 56 LoRA B matrices contain nonzero trained
values. Numbered checkpoints at updates 50, 100, 150, 200, 250, 300 and 350 are
preserved in the same directory. MLX writes the final step-384 weights to
`adapters.safetensors`, without a separate numbered step-384 file.

Rehashing confirmed that the base model, first adapter and frozen native corpus
remain unchanged. `reports/support-training-native.json` and
`reports/support-training-native.log` contain the complete experiment record;
`reports/support-training-native-artifact-check.json` contains the independent
hash, tensor, timing and preservation checks. Its fixed paired evaluation passed
72/102 runs versus 57/102 with the matching base, but made zero refund calls and
failed all 21 refund-required runs. The aggregate improvement concealed a central
workflow regression. [Evaluation evidence](EVALUATION.md) explains the traces and
direct MLX diagnosis; low token loss did not establish correct action routing.

## Inference-scale calibration

We tested adapter gains 0.1, 0.25, 0.5 and 1.0 without modifying learned weights.
The original scale is 20; gain 0.25 applies scale 5. The two exact training
decision probes produced correct refund and high-value escalation calls only at
gain 0.25. Gain 0.1 produced prose without calls, 0.5 produced malformed nested
tool frames, and 1.0 routed the eligible refund to escalation. One validation
refund prefix was also used for token-probability diagnostics during the sweep.

Gain 0.25 was fixed before the complete validation decision audit. It passed
45/48 decisions conditioned on saved expert histories, including all four refund
and five escalation decisions. Failures remained: escalation before lookup for a
bound human request, an incomplete lookup frame, and an unwanted full refund for
a partial-only request. This audit is model selection and diagnosis, rather than
an unseen full-conversation benchmark. Canonical agent fixtures were not used to
select the gain. Full agent evaluation remains a separate check.

The stdlib-only calibration helper copies only the final weights and adjusted
configuration into a fresh directory. It hashes the source, destination and
validation report, refuses existing outputs and symlinks, and labels the operation
as configuration-only inference calibration with **no additional training**:

```sh
python3 scripts/calibrate_support_adapter.py \
  --source .models/support-lora-native \
  --output .models/support-lora-calibrated --gain 0.25 \
  --manifest reports/support-calibration.json \
  --validation-report reports/support-native-gain-diagnosis/validation-gain-0.25/results.json
```

These paths already exist on the development computer; choose fresh output and
manifest paths when repeating the export. Both adapter weight files have SHA256
`6d8cc76a1e9d53c8156b0bdfa1db692f2b7534c33b32b22449ab6b69bf1f2e2f`.
The original adapter and all negative evaluation evidence stay unchanged. Use
the calibrated directory with the local server's `--adapter-path`; inspect the
matched rollout results in [EVALUATION.md](EVALUATION.md) before choosing it.
